# Configurable university-service release — 3 November 2026

The user authorised the release plan and chose configuration-first: no production
domain, identity, database or email services were supplied. Existing checkout,
Flask/Jinja/MongoDB architecture, local data and least-privilege boundaries retained.

Implemented and exercised:

- Real-provider enrolment interface requires signed verified email, exact configured
  issuer and a current one-use university invitation. Ordinary student/officer/triage
  initial roles only; existing-role changes and privileged grants remain controlled.
- Own-profile deletion/account closure requires same-person OIDC max_age=0/auth_time,
  five-minute fresh proof, CSRF, expected version and explicit DELETE confirmation.
  Editable profile/contact values and sessions are removed, pending jobs stopped,
  related cases preserved for review and a minimal closed-principal HMAC/ledger kept.
  Missing identity-protection keys fail closed even in direct service calls.
- Admin team/category/intake configuration has unique category routing, stale-write
  protection and case-history guards. Production routing has no environment fallback.
- Admin invitation/revocation and privacy-review pages; no public staff self-promotion.
  Invitation codes are shown once for secure manual sharing, not emailed automatically.
- Configured category retention/reference, holds, independent approval and explicit
  offline disposal. No real legal retention duration was invented.
- Opt-in authenticated SMTP SSL/STARTTLS transport; default verified certificates,
  protected sender/recipient validation, generic messages, bounded retry/dead state.
  No actual external SMTP was used; TLS ordering/validation/message content were
  checked with controlled substitutes and local delivery remains integration-tested.
- Operator-only production schema/bootstrap, DBA role template, separate web/worker/
  operator settings, readiness checks and encrypted offline quarantine recovery.
  Bootstrap was exercised in the empty dedicated test quarantine, not production.
  Recovery replays post-snapshot closure/disposal, clears sessions, revokes restored
  invitations and suppresses stale mail; protected keys remain outside source.

Actual browser evidence:

- Four signup/profile/first-case/reauthentication/closure/blocked-re-enrolment journeys:
  Chromium/WebKit × 390/1440. Four verified staff-invitation/team-admin journeys at
  the same sizes. Target screenshots omit one-time invitation/password secrets.
- Selected axe tags reported zero violations on the reviewed profile, closed-account
  and invitation pages. This is scoped automation, not full WCAG conformance.
- Existing complete student/staff conversation/referral/closure journeys continue in
  the integrated suite; their historical screenshot directory is regenerated by tests.

Observed corrections: test-owned team audit metadata initially blocked the safe
fixture-reset guard, and test-team teardown left a labelled team behind. Cleanup
was scoped to unique test-owned records; the guard and existing data were preserved.
The direct enrolment service was hardened to require an identity-protection key,
including calls outside Flask. Failed runs were corrected and rerun, not relabelled.

The final suite XML and dependency advisory report are alongside this document.
Historical Stage 16 workload/recovery numbers are not a load test of this expanded
release. External provider integration, deployment, real email delivery, complete-
data/fingerprint expiry/reactivation operations, automated invitation mail/bounce
webhooks and independent security/human accessibility review remain explicitly
limited in the [operator guide](../../handbook/real-service-setup.md).
