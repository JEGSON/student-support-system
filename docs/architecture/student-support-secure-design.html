Student Support System Secure Design Baseline

A practical design for a fictional UK university to manage confidential student support cases using Python, Flask and MongoDB. This baseline contains the six specifications needed before implementation: architecture decisions, data model, access control, workflows, STRIDE analysis and verification.

Status: proposed engineering baseline, ready for review and subsequent implementation with synthetic data. University policy decisions and assessment gaps are recorded in the decision register. No application has been implemented, deployed or security-tested. Numerical targets below are proposed test targets, not measured results.

1 Architecture decisions

Service context and release scope

One university operates academic, finance, wellbeing, disability and accommodation support teams. Students request support; a limited triage function routes requests; assigned staff manage cases; managers allocate work within their teams. The system supports a service with published operating hours, rather than an assumed continuously monitored emergency channel.

The first release includes sign-in, case submission and tracking, limited triage, assignment, student-visible messages, internal notes, status changes, closure, audit and administrative access management. Controlled referrals follow after the core authorisation tests pass. File uploads, unrestricted exports, automated eligibility decisions, AI risk scoring, production student-record integration and broad reporting dashboards are deferred.

Deployment and trust boundaries

The identity and email providers remain separate trust domains even if a deployment places their connectors inside the same network. Application-to-database, application-to-worker data, browser-to-edge and operational-administrator access all require distinct controls.

Operating targets and scaling

Proposed assessment workload: 20,000 synthetic cases, 100,000 messages and 50 concurrent authenticated users for 15 minutes, with a 70% read / 30% write mix. Aim for p95 server response below 2 seconds and unexpected errors below 1%, excluding external identity and email latency. These targets establish a reproducible starting test, not a university capacity claim.

Use bounded pagination, indexes aligned with authorised queries, connection pooling and short transactions. Do not cache sensitive case pages in shared caches. More application instances must share session and rate-limit state. MongoDB replication addresses failover; backups address recovery. Proposed recovery targets are RPO 24 hours and RTO 4 hours, subject to business acceptance. Daily encrypted backups and a restoration exercise must demonstrate those targets; more frequent backup capability is needed if a shorter RPO is agreed.

2 Data model

All identifiers are opaque and generated by the server. An identifier is never an access credential. Store timestamps as UTC instants and display dates in Europe/London, accounting for daylight saving. Enumerations, required fields and types are enforced in database validators as well as application validation. Text is plain text in the first release.

Validation and integrity rules

  • Initial proposed limits: description and message 1–10,000 characters; note 1–10,000; assignment reason 1–1,000; referral summary 1–3,000. Normalise whitespace, reject empty values and unexpected fields. Limit form-body size at edge and application.
  • Only server-controlled fields can set ownership, assignment, timestamps, roles and workflow state. Build database filters from typed, allowlisted values; reject operator objects and arbitrary client query expressions.
  • Case mutations match both id and expected version, then increment version. A conflict produces a review-and-retry response without an automatic overwrite.
  • Case creation, history, audit and outbox entries commit together. Message submission and status consequences follow the same rule. Transaction failure leaves no partial business change. Keep external calls outside transactions.
  • Services check referenced users, teams and cases. Account deactivation preserves attribution and triggers reassignment rather than cascading record deletion.
  • Read-access auditing occurs before content is returned. If the required audit cannot be persisted, deny the sensitive read and show a retry message. Operational failure telemetry uses a separate metadata-only path.

Retention and disposal

Case descriptions, messages, notes and referral summaries are highly sensitive; identity and workflow metadata are confidential; audit and session information are restricted. Retention durations must be supplied by the university. Do not invent a universal period or automatically delete cases with a database expiry index.

A scheduled process identifies records due for review. An authorised retention function checks policy and legal holds, then deletes or anonymises linked records according to an approved schedule. Record disposal without retaining the erased narrative. Backups expire under a documented schedule; restoration must reapply disposal records before normal access resumes. Ordinary note revision history does not prevent an authorised correction or erasure process.

3 Access control specification

Deny by default. Authenticate first, then evaluate action, resource relationship, active membership and lifecycle state. Apply the same scope in case lists, individual views, counts, search, downloads and background tasks. This follows OWASP guidance to validate permissions on every request and consider attributes and relationships alongside roles [S3].

Endpoint and response rules

  • Unauthenticated browser navigation goes to sign-in using a validated local return path. Unauthorised case lookups return a consistent not-found response without revealing whether a case exists. Administrative forbidden actions return a generic forbidden response.
  • State-changing forms require CSRF protection; GET performs no business mutations. Invalid CSRF produces no state change.
  • Student responses use explicit field allowlists. Never serialise database documents directly. Internal-note endpoints are staff-only and still require case-level authorisation.
  • Account disablement and membership revocation take effect on the next request. Recheck current permissions in mutation transactions, using an authorisation revision or equivalent guard so overlapping revocations cannot silently authorise stale work.
  • Staff who are also students must select a clear working context. Student ownership does not unlock staff notes, and role combinations do not bypass case scope.
  • Case pages use Cache-Control: no-store; analytics and third-party tracking are excluded from sensitive pages. Apply CSP, secure cookie settings, clickjacking protection and safe error responses.

Emergency “break glass” access is excluded from the first release. Exceptional access requires an institution-approved, separately audited procedure before it can be introduced. Until then, any safeguarding escalation uses the university's agreed process outside routine case permissions.

Realistic walkthroughs

Financial concern: a student submits a living-cost support request. Finance receives a limited queue item; its manager assigns an officer. The officer begins work, asks a question, receives a reply and records a resolution. Another finance officer cannot read it merely because they work in finance.

Disability support: a student describes a health condition. Only the authorised disability case team can read the narrative. An academic referral contains an approved adjustment-related summary, rather than automatically copying medical details.

Accommodation affecting wellbeing: accommodation staff propose a wellbeing referral. Acceptance creates a separate wellbeing case. Student communication explains the sharing purpose under the university's approved policy; a checkbox is not assumed to establish the legal basis.

Urgent concern: staff record a manual priority and escalation action using the agreed procedure. The application shows operating hours and emergency-routing wording supplied by the institution. It does not promise automated detection, clinical assessment or continuous monitoring.

5 STRIDE threat model

Assets and flows

Protected assets are student identities, case narratives, notes, correspondence, role grants, sessions, audit evidence and service availability. Principal flows are F1 sign-in, F2 submission/viewing, F3 staff updates, F4 database persistence, F5 referrals, F6 notification delivery and F7 administration/operations. Browser input, identity claims, third-party responses and database-returned content require validation appropriate to their boundary.

Risk scale: likelihood and impact are each 1 low, 2 medium or 3 high. Product 1–2 is low, 3–4 medium and 6–9 high. Scores are initial qualitative estimates, not measurements. Residual ratings below are targets conditional on controls and test evidence; they are not accepted risks.

Privacy, ethics and control limitations

STRIDE does not fully capture excessive collection, unjustified sharing or inappropriate secondary use. Collect only support-relevant fields; avoid broad student profiling, automated eligibility decisions and public case statistics. Audit identifiers and team/category information are sensitive even without descriptions. Explain who receives information and provide a route for correction and privacy requests.

For real UK special category processing, the university must establish an Article 6 basis and Article 9 condition, assess additional safeguards and complete a DPIA where processing is likely high risk [S4]. The design does not select those legal grounds. A data-sharing explanation or consent checkbox cannot replace that assessment.

Trade-offs: restricted officer access creates handover work; manager access improves supervision but enlarges the insider-risk surface; audit-before-read may deny access during an audit outage; short sessions can interrupt form completion; replicas do not undo deletion; at-rest encryption does not defeat compromised application credentials. Discuss these explicitly in evaluation. Risk acceptance belongs to named institutional owners.

Tools, evidence and test environments

Planned tools: pytest for services and integration, browser automation for journeys and accessibility checks, a load-test tool for workload evidence, dependency and secret scanners, and a scoped dynamic security scan against the isolated test deployment. Pin tool versions when implementation starts. Mock external email failures, but test transactional behaviour against a real MongoDB replica set rather than a mock that cannot reproduce it.

Evidence records test ID, requirement/threat IDs, commit identifier, environment, fixture version, expected/actual result, timestamp and defect reference. Screenshots and logs must use synthetic information and omit secrets. Negative tests are required, not just demonstrations of successful journeys.

SSDLC checkpoints and release criteria

  1. Before coding: review this baseline, resolve implementation-blocking decisions, convert requirements into backlog items and create the synthetic test matrix.
  2. Each feature: implement its policy and validation, add meaningful tests, review threat impact, update documentation and commit a coherent increment.
  3. Before merging: required tests and scans pass; security-impacting changes receive review. For solo work, record the review method honestly rather than inventing an independent reviewer.
  4. Before assessment submission: required workflows and authorisation tests pass; no unresolved critical/high security defect without explicit documented disposition; secrets absent; installation, evidence, AI-use statement and ZIP verified.
  5. Before real deployment: institution approves privacy grounds, retention, safeguarding, access owners and residual risks; hosting and incident response are established; recovery tested. Assessment acceptance alone does not establish production readiness.
