STUDENT SUPPORT SYSTEM DEVELOPMENT PROMPTS
Version 1.1 | 2 November 2026

HOW TO USE

Use the master prompt first, followed by one numbered prompt at a time. In a new chat, provide the master prompt and the current stage together. Keep completed work and evidence in the project repository. Each numbered prompt authorises only that stage; it does not authorise production deployment, handling real student information, pushing to a remote repository, or contacting third parties.

The sequence is: establish the repository; define the visual design and user experience; create the runtime and design system; establish identity and access; build a complete core case journey; extend communication and referrals; add operational controls; verify; package and hand over.

FRONTEND QUALITY CONTRACT

The user explicitly requires a crisp, polished, professionally designed interface. Visual design is a deliverable, alongside secure behaviour. Establish the visual direction before feature implementation and use the shared design system in every feature. Stage 14 is refinement and accessibility verification, not the first time design is considered.

Use the Flask/Jinja architecture with reusable templates, semantic HTML, organised CSS and progressive enhancement. Avoid a framework change solely for appearance. The interface should feel calm, precise and trustworthy for students discussing sensitive concerns. Proposed direction: warm off-white canvas, deep navy text, restrained teal accents, generous spacing, subtle borders, carefully balanced typography and consistent component geometry. Document final tokens rather than scattering arbitrary values across stylesheets. Avoid generic template styling, gratuitous gradients, heavy shadows, overcrowded dashboards, irrelevant imagery and excessive animation.

Every screen needs purposeful hierarchy, clear navigation, readable content, useful actions, responsive behaviour and accessible contrast/focus. Include loading or processing feedback where relevant, empty, validation, error, success, unauthorised, expired-session and archived/closed states. Never fabricate live-looking metrics, testimonials or support promises to fill a layout. Display only data the user is authorised to see.

Assess the actual rendered pages at representative phone, tablet and desktop widths. Capture synthetic-data screenshots where tools permit; review alignment, wrapping, hierarchy, contrast and interaction states, then fix visible issues. Record what was inspected and any inspection limitation. Do not claim the site is polished merely because CSS exists or tests pass.

Implement only the numbered stage requested. Make routine reversible implementation choices and document them. Ask only when a missing decision blocks safe progress; continue independent work. If a change conflicts with the baseline, explain the conflict and record a justified decision before implementation. Update the threat model and affected tests when scope or security boundaries change.

For each stage:
- Inspect current implementation and prior stage evidence before changing it.
- Implement a coherent working increment, including necessary negative tests.
- Run checks appropriate to the changed behaviour and report actual results.
- Maintain a requirements/threat/test traceability register, decision log and development record. Maintain an AI-use log consistent with known policy; mark the full policy as pending if unavailable.
- Keep documentation and diagrams aligned with actual behaviour.
- Never claim an unrun test passed or a control exists without evidence.
- Do not create empty tests, fabricate screenshots or construct fake Git history.
- If Git is available and local commits are permitted by project instructions, make one or more meaningful commits after checks pass. Do not push, publish, deploy or send messages without separate authorisation. If commits cannot be made, report why and give a suggested commit message.

End with: implemented behaviour; files changed; actual checks/results; residual risks or blockers; and the next stage. Stop after the requested stage. A stage is incomplete if its required security or verification work is unresolved; do not conceal this by advancing the stage number.

PROMPT 12 — CONTROLLED CROSS-TEAM REFERRALS

Apply the master prompt. Implement the referral process after core authorisation and case tests pass.

Acceptance creates a separate New target case and records the link atomically. The source case remains unchanged. Rejecting or withdrawing a referral must follow an explicit reviewed state model.

The target team must not inherit access to source descriptions, messages or internal notes. Repeat or concurrent acceptance creates only one target case. Sharing text is deliberate and minimal; record that institutional privacy and sharing grounds are still required before real use.

Test source/target manager scope, officer restrictions, rejection, repeat acceptance, rollback, target case ownership and source-note non-disclosure. Update WF-09, T06 and V04/V10.

STAGE PROGRESSION RULE

Use the architecture/design artefacts as a living baseline and retain evidence of justified changes.
